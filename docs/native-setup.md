# Native runtime setup

Managed process supervision currently supports macOS and Linux. Other hosts can inspect status but cannot start managed installation or sign-in.

Creation and runtime settings on web, Electron and mobile expose **Set up runtime** for the selected local bridge or registered host. Opening it checks that specific host. **Prepare install** and **Prepare sign-in** create a plan; they do not execute the plan or enable host access. The API accepts provider-neutral intents and registry IDs, never executable arguments, filesystem destinations, environment variables or permission grants.

The plan shows the exact command, destination and a host-local approval command. Run that command in a terminal on the selected host, from this checkout, then inspect the plan and type `yes` when prompted. For example:

```sh
pnpm host:setup --data-dir /path/to/host-data --session <setup-session-id>
```

An interactive terminal is required. Consent is a private file under the chosen host data directory and cannot be granted through the web/mobile API. The host bridge must already have local host consent. A plan expires after fifteen minutes. Approval is consumed once; restarting the host never replays an approved plan. Selecting another host or account clears the UI's previous session and challenges. Opening setup again on the same host recovers that owner's session while the host process remains alive.

Installation runs npm with a fixed provider package, an explicit prefix, a private cache, no lifecycle scripts and no global installation. npm must already exist on the host. Each provider uses `native-tools/<provider>` under the selected host data directory, including its home, configuration, cache and temporary directories. The installer never replaces a separately installed CLI. There is no automatic install, update, package download or account sign-in at launcher startup, during status checks, or in tests.

Sign-in uses an isolated profile under the same directory, even when it reuses an existing CLI executable. The existing default CLI profile is preserved. Codex uses its supported device authorization command. Its fixed HTTPS verification page and one-time device code are returned only for the active, owner-bound setup session; arbitrary output, OAuth callback codes, bearer credentials and provider errors are discarded. Claude Code uses its supported browser sign-in command; continue in the browser on the host. On macOS the provider may use an isolated configuration-specific keychain entry. No OAuth code or API key is accepted through chat or the setup API. ACP has no universal installation or login command: its private host configuration and installed provider remain operator-managed, as described in [Native runtimes](native-runtimes.md).

After installation the executable resolver can use the host-managed CLI. After sign-in succeeds, it selects that provider's isolated profile. Runtime status still verifies the actual CLI account through the protocol adapter. No provider credential is copied into the database or returned in a setup view.

**Cancel setup**, local host-access revocation and clean shutdown kill and await only setup-owned process groups. Registry revocation also writes a durable tombstone, so previously approved plans cannot become valid again after restarting the host. Account and Space deletion revoke each affected owner's setup scope, including local-bridge plans, before deleting their records; another owner's scope remains available. Deletion requires confirmed setup cleanup from every affected host.

When account deletion also removes a Space, the final deletion decision commits before former owners' setup scopes are revoked. Memberships admitted before that decision keep the Space shared; new memberships are refused afterward. If a host acknowledgement is lost, retrying continues the committed deletion instead of reopening a Space with revoked setup scopes. The database enforces this decision for older membership writers too. During an upgrade from the earlier transaction-only cleanup implementation, drain account deletions running on old API processes before enabling the new cleanup path: the migration cannot change an old process's already-started external revocation.

A private provider lock is acquired immediately before spawning and the running journals are checked again under that lock. Independent bridge processes sharing a data directory cannot install or sign in to the same provider profile concurrently. A running-setup journal is written before spawning; verified cleanup removes the journal and releases only the lock owned by that session. If a host crashes, an unresolved journal or provider lock prevents another setup for that provider and prevents revocation from claiming verified cleanup. The host operator must inspect and stop any remaining setup processes before resolving those files locally. The application never guesses a PID or kills an unrelated user process. Terminal session history is bounded; old completed or cancelled sessions may become unavailable without preventing new setup plans.

Verification uses fake provider output, fake child processes and a small owned Node process. It covers local consent, replay, command/path injection, private file modes, symlinks, owner/host/provider binding, stale UI responses, expiry, cancellation, crash journals and durable revocation. No real provider install or sign-in is exercised. Real package installation and browser/device authorization still require operator acceptance on each target platform.
